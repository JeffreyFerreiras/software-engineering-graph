# Standalone Software Engineering Graph source repository

## Design status

READY for Architect review and implementation.

This design creates an exact local source repository copy of the existing profile skill plus seven
generic profile-agent definitions. It does not redesign, install, migrate, bootstrap, publish, or
operate the workflow.

## Current state and constraints

The approved source is supplied through two explicit directory inputs:

- `SEG_SOURCE_SKILL`, containing `SKILL.md`, OpenAI skill metadata, `scripts/graphctl.py`, the
  `graph_engine` runtime, four JSON schemas, six unittest modules, and the golden-trace fixture.
- `SEG_SOURCE_AGENTS`, containing reusable role TOMLs and project-specific specialist TOMLs. Only
  the seven explicitly named generic TOMLs are in scope.

The copied runtime is a Python standard-library/SQLite control ledger. Its current engine code owns
the CLI grammar, numeric engine/state/schema versions, stable identifiers, route topology, risk tags,
specialist protocol identifiers, policy validation, role capability ceilings, npm/src assumptions,
artifact rules, storage discovery, state transitions, joins, replay behavior, and failure codes.
All of that is established behavior and remains unchanged.

The source contains `__pycache__` directories and `.pyc` files generated by local execution. These
are not source and must not be copied. Run databases, graph inboxes, secrets, environment files, and
other profile state are also excluded.

Constraints:

- Destination: the standalone source repository checkout.
- The current profile skill, profile agents, and all consumer repositories remain untouched.
- Preserve approved source bytes where practical. The only approved source-content change is the
  `SKILL.md` heading, from a generation-labelled heading to `# Software Engineering Graph`.
- New repository documentation uses only the canonical human-facing name
  `software-engineering-graph` or “Software Engineering Graph.” Numeric protocol, engine, state, and
  schema versions remain unchanged.
- Optional audio, iOS, release, and security specialists remain identifiers and contracts in copied
  engine code, schemas, tests, and fixtures. Their project-specific agent TOMLs and consumer policy
  configuration are not packaged.
- Python 3.9+ standard library only. Validation sets `PYTHONDONTWRITEBYTECODE=1`.
- No repository policy template, installer, updater, migration, bootstrap, manual profile-copy
  guidance, release automation, marketplace metadata, license, network access, or remote action.

### Requirements and acceptance criteria

- **AC-01, source parity:** every approved skill source file is present at the same relative path and
  byte-identical to the profile source, excluding generated/cache/state files and the approved
  `SKILL.md` heading change.
- **AC-02, exact profile-agent set:** `profile-agents/` contains byte-identical copies of exactly
  `impact_mapper.toml`, `tech_lead.toml`, `software_architect.toml`, `senior_engineer.toml`,
  `code_reviewer.toml`, `test_engineer.toml`, and `security_reviewer.toml`; no other agent TOML is
  packaged.
- **AC-03, no executable behavior change:** engine modules, `graphctl.py`, schemas, tests, and
  fixtures preserve current bytes and behavior, including optional specialist protocol identifiers,
  current policy contracts, npm/src assumptions, storage discovery, and CLI behavior.
- **AC-04, in-place source validation:** with bytecode disabled, imports,
  `python scripts/graphctl.py --help`, and an explicitly enumerated standalone acceptance test set
  work from the checkout. The full copied suite is preserved but is not an acceptance command. No
  operational `init`, `status`, or other stateful graph command is claimed or run against the
  standalone checkout.
- **AC-05, clean repository:** a final hygiene scan finds no cache, bytecode, virtual environment,
  database, run-state, inbox, secret, environment, coverage, build, or temporary artifacts outside
  `.git`; `.gitignore` covers those categories.
- **AC-06, canonical documentation:** README, AGENTS, this design, and the `SKILL.md` heading have no
  human-facing version-generation branding. Numeric compatibility values and identifiers inside
  preserved protocol sources are explicitly allowed.
- **AC-07, isolation:** hashes for the source profile skill and source profile-agent files are
  unchanged after copying and validation. Any one-time consumer-repository verification remains
  outside durable tests, uses read-only hardened Git settings, and exposes only a status digest.
  No external or remote system is contacted.

### Non-goals

- Changing engine topology, tags, specialist identifiers, capabilities, policy invariants, storage,
  paths, schemas, tests, fixtures, npm assumptions, source-root assumptions, or runtime behavior.
- Making the engine generic by deleting application-specialist protocol support.
- Shipping app-specific audio, iOS, or release agent profiles or consumer repository configuration.
- Generating `.codex/engineering-graph.json`; consumer policies remain owned by consumer repositories.
- Running an operational graph from this source checkout or redirecting graph runtime state.
- Installing or copying this repository into the current profile, documenting profile-copy commands,
  synchronizing profile drift, or migrating active or retained runs.
- Modifying consumer AGENTS files, bootstrapping repositories, committing, pushing, publishing,
  releasing, deploying, creating marketplace entries, or adding a license.
- Adding package managers, third-party dependencies, build systems, installer manifests, release
  metadata, or speculative management scripts.

## Proposed design

### Canonical repository layout

```text
software-engineering-graph/
  .gitignore                         # new, minimal local-artifact exclusions
  AGENTS.md                          # new, repository contributor constraints
  README.md                          # new, source-repository usage and validation
  SKILL.md                           # copied; heading canonicalized only
  agents/
    openai.yaml                      # copied byte-for-byte
  profile-agents/
    impact_mapper.toml               # copied byte-for-byte
    tech_lead.toml
    software_architect.toml
    senior_engineer.toml
    code_reviewer.toml
    test_engineer.toml
    security_reviewer.toml
  graph_engine/
    __init__.py                      # copied byte-for-byte
    cli.py
    config.py
    contracts.py
    evidence.py
    ids.py
    planner.py
    state.py
    validator.py
  references/
    branch-envelope.schema.json      # copied byte-for-byte
    impact-map.schema.json
    repository-config.schema.json
    task-brief.schema.json
  scripts/
    graphctl.py                      # copied byte-for-byte
  tests/
```

The implementation copies an explicit allowlist of source files. It does not recursively mirror the
profile skill or agents directory. This prevents generated and out-of-scope files from entering the
repository while making parity review deterministic.

No repository policy template is added. The copied tests and helpers are retained byte-for-byte as
source evidence. A real consumer's `.codex/engineering-graph.json` remains source-controlled by that
consumer.

### Source parity contract

Files in these destination groups must match their source bytes exactly:

- `agents/openai.yaml`;
- all `graph_engine/*.py` modules;
- `scripts/graphctl.py`;
- all four `references/*.schema.json` files;
- all six `tests/test_*.py` modules;
- `tests/fixtures/result-manifests/golden-traces.json`;
- all seven `profile-agents/*.toml` files.

`SKILL.md` must match after normalizing only its first heading line to
`# Software Engineering Graph`. Frontmatter, instructions, commands, protocol terminology, and all
remaining bytes are preserved. Numeric `schema_version`, `STATE_SCHEMA_VERSION`, `ENGINE_VERSION`,
`g2-` stable-ID patterns, or other compatibility values are not generation branding and are not
changed.

The source-parity validation compares relative-path sets, file sizes, and SHA-256 digests. For
`SKILL.md`, it compares the destination against an in-memory source copy with only the approved first
heading replacement. It reports sorted relative paths for missing, extra, or changed source files.
This validation is a one-time implementation command or review check, not a new checked-in installer,
manifest, or synchronization tool.

### Optional specialist boundary

The engine's application-specialist names remain because they are part of current topology and
contract validation. The copied tests continue encoding coverage for those protocol branches. This repository does
not include their profile agent definitions:

- `audio_realtime_specialist.toml` is not copied;
- `ios_platform_specialist.toml` is not copied;
- `release_operations_reviewer.toml` is not copied.

The generic `security_reviewer.toml` is copied because it is one of the seven required reusable
roles. Absence of the other agent TOMLs does not change engine code or claim that every possible
consumer policy is runnable with only this repository. Consumers that enable optional specialist
tags own the corresponding agent availability and policy integration.

### Minimal new repository files

`README.md` states:

- this is the canonical source repository for the copied workflow;
- Python 3.9+ and standard library are required;
- source-level use from this checkout is limited to imports, tests, and
  `python scripts/graphctl.py --help`;
- operational graph commands require a separate consumer repository with its own policy and may
  discover profile-local state, so the README does not demonstrate or claim operational execution;
- validation commands use `PYTHONDONTWRITEBYTECODE=1`;
- the profile installation remains separate and is not modified or installed by this repository.

README contains no installation, manual-copy, bootstrap, migration, publishing, release, or remote
instructions.

`AGENTS.md` instructs contributors to preserve source parity and executable behavior, keep the seven
packaged profile-agent files exact, retain optional specialist protocol identifiers, use stdlib
Python, avoid generated/state/secret files, run only the enumerated standalone acceptance tests with
bytecode disabled, run hygiene last, and avoid profile, consumer-repository, and remote mutations
without separately approved scope.

`.gitignore` covers `__pycache__/`, `*.py[cod]`, common Python test/tool caches, virtual environments,
coverage/build output, `.env*`, key/certificate files, `*.db`, `*.sqlite*`, and graph run/inbox state.
It does not ignore copied source, tests, fixtures, schemas, or profile-agent TOMLs.

## Interfaces and failure modes

### Preserved runtime interface

The sole runtime entry point remains byte-identical:

```text
python scripts/graphctl.py --repo <consumer-repository> [options] <command>
```

Its existing imports and CLI grammar are unchanged. This design does not redefine commands, output
JSON, exit codes, persistence paths, permission acknowledgements, or failure semantics.

Supported in-place claims are deliberately narrow:

1. importing `graph_engine` modules from the checkout;
2. displaying `python scripts/graphctl.py --help`;
3. running only the explicitly enumerated standalone acceptance tests defined below.

Operational `init`, `status`, `resume`, record, join, complete, block, and abort behavior remains in
the source and tests, but it is not invoked against this standalone checkout during packaging. Such
commands require a consumer repository policy and can use existing profile storage discovery.

The full copied unittest suite is not run as standalone acceptance because two preserved source
couplings resolve installation-specific paths:

1. `tests.test_support.GraphCase.setUp` reads a hard-coded consumer policy. Every copied test class
   deriving from `GraphCase` therefore depends on that consumer checkout even though its ledger and
   artifacts are otherwise created under `TemporaryDirectory`.
2. `tests.test_state.StateTests.test_default_store_uses_profile_root_not_skill_directory` resolves
   and asserts the installed profile root through `installed_codex_home()` and default `StateStore()`
   discovery.

Both cases remain byte-identical source. They, and the copied classes transitively using the shared
fixture, are not selected by the standalone validation command. This exclusion is an acceptance
boundary, not a skip marker or edit to copied tests.

### Data and control flow

No new application data flow is introduced. Source files move once from the approved profile paths
to matching repository paths. After the copy, validation reads both trees and compares digests; it
writes only ordinary temporary test data under test-managed temporary directories.

At runtime, the preserved flow remains `graphctl` -> consumer policy/task artifacts -> engine
validation/planning/state -> profile-local SQLite ledger/inbox. This design neither redirects nor
wraps that flow.

### Failure handling

- A missing approved source file, unexpected source path, digest mismatch, or unauthorized
  destination file blocks source-parity acceptance. Nothing is repaired in the source profile.
- If the profile source changes during copying, before/after source hashes differ and implementation
  stops for a new stable checkpoint rather than combining versions.
- If `SKILL.md` differs beyond the approved heading normalization, parity fails.
- If any engine, script, schema, test, fixture, or profile-agent destination differs from its source,
  parity fails.
- If tests try to resolve the real profile rather than temporary storage, isolation validation fails.
- If bytecode, cache, database, inbox, state, secret, environment, coverage, build, or temporary files
  exist in the repository after tests, final hygiene fails and the generated artifact must be removed
  before acceptance. Hygiene never deletes broadly or modifies the source profile.
- Missing optional project-specific agent profiles are expected package scope, not a runtime fallback.
  No role substitution or topology change occurs.

## Rollout, rollback, and observability

### Rollout

1. Capture read-only before hashes for the approved profile skill files and seven source agent TOMLs.
   If a Supervisor also verifies a consumer repository, do so outside durable tests with optional
   locks disabled, fsmonitor/untracked cache/maintenance disabled, sanitized Git configuration and
   environment, and internally hashed output that never prints raw filenames.
2. Copy the explicit allowlisted skill sources and seven profile-agent files to the canonical layout,
   excluding caches and state.
3. Normalize only the `SKILL.md` heading.
4. Add minimal README, AGENTS, `.gitignore`, the standalone acceptance test, and retain this design.
5. Run source-parity comparison before behavioral validation.
6. Set `PYTHONDONTWRITEBYTECODE=1`; run the deterministic, explicitly enumerated standalone
   acceptance selection. Do not invoke unittest discovery or the full copied suite.
7. Re-run source-parity comparison to detect accidental test or repair changes.
8. Run forbidden-artifact and canonical-document hygiene last.
9. Compare source profile hashes to their before snapshot and inspect the local destination diff.
   Compare only the opaque before/after digest for any separately authorized consumer check.

No commit, install, profile mutation, consumer-repository mutation, network call, publish, release,
deployment, or marketplace action is part of rollout.

### Rollback

Rollback before any later authorized commit is limited to restoring or removing destination files in
this new repository with non-destructive Git-aware methods that preserve unrelated changes. There is
no profile, database, consumer-policy, installation, migration, or remote rollback because none is
changed.

### Observability

Evidence consists of:

- sorted parity results with relative paths and SHA-256 digests;
- exact deterministic selection commands, Python version, exit codes, and unittest summaries;
- final sorted forbidden-artifact/human-label scan results;
- before/after read-only evidence that source profile paths were untouched and, when separately
  checked, only an opaque consumer-status digest;
- local target file-allowlist and scoped diff checks.

No telemetry, operational ledger status, installation state, migration journal, publishing record,
or network logging is added.

## Test strategy

### Acceptance mapping

- **AC-01:** enumerate the approved source and destination relative paths in sorted order. Compare
  sizes and SHA-256 digests, normalizing only the source `SKILL.md` heading in memory. Fail on missing,
  extra, or changed copied files, and reject root-level files outside the exact allowlist.
- **AC-02:** assert `profile-agents/` contains exactly the seven required TOML names and compare each
  digest with `SEG_SOURCE_AGENTS/<name>.toml`.
- **AC-03:** exact file hashes provide the primary evidence that runtime behavior was not redesigned.
  The copied tests remain source parity evidence for topology, specialists, risk tags, policies,
  npm/src assumptions, schemas, CLI, storage discovery, state, joins, replay, and failures; their
  presence is required, but the full suite is not executed for standalone acceptance.
- **AC-04:** `tests.test_standalone_acceptance.StandaloneAcceptanceTests` contains only the three
  methods named in the command below. `test_source_parity` reads and hashes the approved source set.
  `test_imports_and_help_do_not_mutate_sources` snapshots the approved profile-source hashes, runs
  imports and `graphctl --help` in subprocesses with `CODEX_HOME`, `TEMP`, and `TMP` redirected to one
  `TemporaryDirectory`, then requires identical after snapshots and no files beneath the temporary
  profile. `test_hygiene` is read-only and is run separately, last. No method invokes Git, reads a
  consumer repository, imports `test_support`, invokes copied `GraphCase` tests, or runs an operational
  graph command.
- **AC-05:** after all tests, scan the repository recursively except `.git` for forbidden directory
  and filename patterns, including existing `*.egg-info` directories. Check that `.gitignore` covers
  each generated category. Hygiene is the last validation so successful acceptance leaves the
  repository clean.
- **AC-06:** scan only new human-facing documents and the `SKILL.md` heading for version-generation
  labels. Do not scan preserved engine/schema/test values as branding or rewrite numeric
  compatibility contracts.
- **AC-07:** compare before/after hashes for the approved source profile files and source role TOMLs.
  Durable acceptance has no consumer-repository or Git dependency. A separately authorized one-time
  consumer check compares only hardened, internally hashed status output. Record that no network or
  remote command was run.

The source paths are explicit environment inputs to the acceptance test, so the test fails rather
than guessing or falling back to a live path. The test rejects a source root that is inside the
destination, rejects a temporary root that contains or is contained by a source root, and opens all
parity inputs read-only. Before subprocesses run, it records source file hashes; after they exit it
proves those observations are unchanged. The subprocess environment sets
`PYTHONDONTWRITEBYTECODE=1`, points profile and temporary variables only at the created temporary
root, and does not inherit a writable profile override.

Deterministic validation environment, selection, and order:

```powershell
$env:PYTHONDONTWRITEBYTECODE = '1'
$env:SEG_SOURCE_SKILL = '<absolute-path-to-approved-skill-source>'
$env:SEG_SOURCE_AGENTS = '<absolute-path-to-approved-agent-source>'
python -m unittest -v `
  tests.test_standalone_acceptance.StandaloneAcceptanceTests.test_source_parity `
  tests.test_standalone_acceptance.StandaloneAcceptanceTests.test_imports_and_help_do_not_mutate_sources
python -m unittest -v `
  tests.test_standalone_acceptance.StandaloneAcceptanceTests.test_hygiene
```

The selection is literal and ordered; no wildcard, discovery, dynamic test enumeration, or copied
test module is allowed in standalone acceptance. The second command is hygiene last. A missing source
path or inability to isolate temporary/profile paths is `BLOCKED`, not permission to broaden the
selection. The implementation must not modify copied source to make an excluded coupled test
runnable.

## Alternatives and tradeoffs

### Remove application-specific specialist identifiers

Rejected. That would change topology, policy validation, fixtures, and executable behavior. The
requested boundary excludes specialist agent profiles, not existing protocol identifiers in the
copied workflow.

### Add a generic repository policy template

Rejected. Current policy contracts include consumer-specific assumptions, and consumer repositories
own their policy. A template would imply a new supported configuration and broaden scope.

### Add installation or manual-copy guidance

Rejected. The current task prepares source only and must leave the profile untouched. Installation,
drift, backup, permissions, and migration need separate authority and design.

### Recursively copy the profile directories

Rejected. Recursive copying would import bytecode/caches and could include out-of-scope specialist
agents or local state. An explicit allowlist gives exact parity without broadening the package.

### Rewrite versions, IDs, npm/src assumptions, or storage paths

Rejected. These are executable protocol and compatibility contracts. Human-facing heading
canonicalization does not justify a runtime migration or portability redesign.

### Add packaging, bootstrap, release, or publishing automation

Rejected as unauthorized and unnecessary for a local source repository.

## Assumptions and human decisions

- The inspected profile skill and seven role TOMLs are the authoritative source checkpoint. If they
  change before or during implementation, the Supervisor must approve a fresh checkpoint.
- Canonical naming without generation suffixes applies to new repository documentation and the
  `SKILL.md` heading. It does not authorize changes to numeric protocol/state/schema versions, semantic engine
  versions, stable IDs, tests, or fixtures.
- Optional app specialists remain supported protocol identifiers in copied engine/tests. Their agent
  profiles and consumer configuration are intentionally absent; consumers enabling them remain
  responsible for those pieces.
- The copied tests are permitted to exercise operational flows only inside their existing temporary
  test repositories and profile roots when a future consumer-specific validation explicitly provides
  the required live policy/profile context. They are not part of standalone acceptance.
- Source parity takes precedence over cleanup or refactoring. Any executable-source change discovered
  as necessary during implementation is a design blocker, not an implicit repair.

No human decision blocks implementation under this exact-copy scope.
